# 26-10-15测试优化

日期：2026年10月15日
对象：DCMA 网页 Agent，公共仓库版本 `668598cec`
模型：DeepSeek Flash（`deepseek/deepseek-flash`）
依据：[详细测试报告](REPORT.md)、[测试用例](TEST-CASES.md)、[逐项结果](TEST-RESULTS.md)
性质：测试后的调优建议，尚未实施，不代表产品已经具备文中建议的能力。

## 一、调优目标与基本原则

本轮32次有效评估中，24次通过、6次部分通过、2次失败。样本包含重复执行，该比例不能当作生产成功率。

最值得优先调优的是**任务完成判断、数据获取粒度、统计计算和证据使用**。这些能力直接影响 Agent 能否解决问题，表达的专业性与简洁性也会随之改善。

调优的核心是让 Agent 根据用户目标，选择合适的数据和工具，形成有依据的结论，并识别何时已经完成任务。保持以下原则：

- 允许合理的工具路径差异，不强制每个问题执行同一套步骤。
- 让计算工具保证算术准确，让 Agent 自主选择分析对象、范围和解释方式。
- 用权限、数据范围和执行预算保护运行边界，不用大量固定话术替代任务能力。
- 按任务评价切题性，不要求所有回答采用统一字数或固定段落模板。
- 先继续使用当前 Flash，通过同一批测试验证改进，再判断模型本身的能力限制。

## 二、详细调优方向

### 1. 修正任务完成判断机制

**优先级：最高。**

#### 测试发现

跨电机比较已经取得两台设备的数据，却只留下39个字符的查询过程，接口仍返回 `done`。目前服务主要判断“有没有输出文字”，不足以说明任务已经完成。

#### 调优建议

将执行状态区分为正在获取证据、已形成答案、部分完成、执行失败、用户中止。识别模型因输出长度限制结束的情况，避免将已有过程文字作为最终成果。

任务中断后，保留已经取得的有效数据，按错误类型决定是否进行有上限的恢复。恢复后仍无法完成，应明确说明已经取得什么、还缺什么。

#### 验收重点

“比较两台设备”应给出比较结果，或说明无法比较的具体原因。HTTP 200、存在文字、流正常结束，均不能单独作为成功标准。

### 2. 让数据获取粒度与问题匹配

**优先级：最高。**

#### 测试发现

“当前电机温度是多少”只需要最新温度及采集时间，但当前工具返回目录和100条多指标采样，约56.8KB。该用例两轮模型累计处理约2.44万 token。

#### 调优建议

让数据工具支持按需要选择字段、时间范围和采样数量，由 Agent 自主选择。

| 用户任务 | 通常需要的数据 |
|---|---|
| 查询当前温度 | 最新温度、采集时间、来源 |
| 查询设备信息 | 设备标识及已确认档案信息 |
| 分析近期变化 | 指定指标、明确时间范围的采样 |
| 比较两台设备 | 两台设备可比较的快照或窗口统计 |
| 调查异常 | 异常时段及关联指标 |

避免所有问题默认取得完整窗口，也不需要为每种问法增加一套专用答案。

#### 验收重点

简单查询的数据量、输入 token 和耗时明显下降，同时保持读数、来源和时间准确。

### 3. 把统计计算交给可执行工具

**优先级：最高。**

#### 测试发现

运行报告将实际转速均值写成约795，同次100条数据独立计算得到800.034；另一个温度统计用例又计算正确，说明模型计算表现不稳定。

#### 调优建议

提供通用统计能力，由 Agent 决定计算哪个指标、哪段时间，再由程序执行。可按实际任务逐步支持：

- 有效样本数、缺失数量。
- 最小值、最大值、平均值。
- 首末变化、变化幅度。
- 超过阈值的数量及对应时段。
- 两个指标的差值、设定值与实际值偏差。
- 必要的分位数、波动程度。

统计结果同时带上数据范围和计算口径。空值不能默认当成0；严格大于与大于等于必须区分；中间计算保留精度，展示时再舍入。

这里需要的是通用计算能力，不是为每一种用户问题硬编码答案。

#### 验收重点

统计结果能通过独立程序复算，而非只要求数值看起来合理。

### 4. 建立明确的证据覆盖范围

**优先级：最高。**

#### 测试发现

Agent 曾根据最新一条记录的状态码，声称100条记录的状态码全部为0，但取得的100条采样矩阵不包含这些状态字段。

#### 调优建议

工具结果明确说明：

- 哪些字段来自最新记录。
- 哪些字段覆盖整个采样窗口。
- 哪些结论来自统计。
- 哪些字段缺失或未查询。
- 数据是否截断，是否仍有更早记录。

使 Agent 能区分“最新一次故障码为0”与“整个窗口内故障码均为0”。

#### 验收重点

每项重要结论都有对应证据覆盖，不能由单点扩大到窗口，再由窗口扩大到全历史。

### 5. 按任务调整模型推理与输出预算

**优先级：高。**

#### 测试发现

转速趋势分析和跨设备比较都在最后一轮耗尽4096个输出 token，没有留下有效的最终结论。

#### 调优建议

先减少无关输入和模型手工计算，再评估预算：

- 简单查询尽快返回结果。
- 趋势、比较任务使用整理过的证据。
- 完整报告允许更多分析和输出空间。
- 识别长度耗尽，利用已有证据恢复，避免重新查询全部数据。

如果当前 Flash 接口和 SDK 支持调整推理强度，可通过实验比较不同设置。实施前需要核对实际支持情况，不能假定某个参数一定有效。

#### 验收重点

复杂任务形成结论的比例提高，成本和延迟仍可接受。避免仅通过不断增加 token 上限掩盖执行低效。

### 6. 减少重复查询目录，优化工具选择

**优先级：高。**

#### 测试发现

当前提示词要求设备问题先查目录，目录会返回多个来源的大量字段信息。对于结构已知的单指标查询，这一步价值有限。测试中也有一次单温度查询只调用一个工具，核心读数仍然正确。

#### 调优建议

将相对稳定的元数据与不断变化的设备读数分开处理：

- 表结构、字段定义可缓存，并按需要刷新。
- 当前读数仍需要符合用户问题的新鲜证据。
- 查询失败、字段不存在或结构变化时，再重新发现目录。
- 已明确不支持的控制请求，可直接说明能力边界。

工具选择围绕“还缺少什么证据”，无需每次执行相同清单。

#### 验收重点

减少没有信息增益的调用，不机械要求所有任务只能调用一次工具。

### 7. 补齐 Agent 与展板之间的能力缺口

**优先级：高。**

#### 测试发现

展板已经具备历史异常、事件区间和时长查询逻辑，Agent 主要依赖近期采样和受限原始行查询，无法完成完整历史事件统计。

#### 调优建议

优先复用已有后端能力，让 Agent 按需查询：

- 指定时间范围内的故障、报警事件。
- 事件开始、结束及最后观察时间。
- 指定代码的出现次数和累计观察时长。
- 异常前后的关联指标。

事件次数、非零采样点数量、累计时长保持不同口径，不能互相替代。

#### 验收重点

全历史问题可以调用对应能力，并明确覆盖范围；不能把最近100条记录包装为完整历史结论。

### 8. 改进筛选能力，减少近似条件转换

**优先级：高。**

#### 测试发现

当前原始行查询只支持 `=`、`>=`、`<=`。模型曾使用 `fault_code >= '1'` 近似表示非零代码，对于字符串故障码容易出现语义偏差。

#### 调优建议

根据实际任务补充必要查询语义，例如非零代码、空值检查、时间区间，以及明确的排序和分页。

这些能力由后端验证字段、范围和条件，继续保留只读、参数绑定和结果大小限制。

#### 验收重点

Agent 能直接表达想查询的对象，减少容易失真的条件转换，同时保持数据访问边界。

### 9. 区分数据质量问题与设备故障判断

**优先级：高。**

#### 测试发现

存在两种过度判断：将 `null` 直接归因为未采集、未入库；将 `-200` 直接认定为无效占位或量程异常。这些可以作为排查假设，但单凭数值无法确认原因。

#### 调优建议

区分观察到的事实、可能解释、已经验证的原因。允许 Agent 自主提出假设，同时说明验证假设需要什么证据。

没有额定值、阈值或测点规范时，避免从数值看起来不大直接推导设备正常。

#### 验收重点

保留原始值，允许合理分析，同时不把猜测写成事实。

### 10. 建立可信领域元数据，统一名称、单位和时间口径

**优先级：高。**

#### 测试发现

展板显示单位，Agent 却常说单位未确认，有时先使用单位再声明只是猜测；时间上也混用了查询时间、采集时间，以及 UTC 和北京时间。

#### 调优建议

逐步建立共享的数据定义，包含中文名称、工程单位、来源类型、时间解释，以及定义是否已经确认、确认依据是什么。

明确区分：

- 数据名称与已核实的设备型号。
- 当前采样与历史采集。
- 采集时间、入库时间、查询时间。
- 时间戳明确的时区与数据库业务口径是否已经确认。

例如，带 `Z` 的时间戳明确表示 UTC，不应再笼统说时区未知；设备名称包含“G120”，也不能直接作为型号资料已经核实的依据。

#### 验收重点

Agent 与展板使用同一套定义；已确认的信息不反复怀疑，未确认的信息不擅自补全。

### 11. 让回答围绕任务自然收敛

**优先级：高。**

#### 测试发现

简单问题经常扩展到其他温度、趋势、状态字、台账及多段限制。多余内容还产生新的错误，例如把接近低位的温度描述为区间中位附近。

#### 调优建议

将“回答是否已经足够解决问题”纳入任务结束判断：

- 所问读数已经取得，即可回答。
- 用户问趋势，再补充变化证据。
- 用户问原因，再进行关联调查或澄清。
- 用户要求完整报告，再展开统计和建议。

通过切题性评审改善简洁性，不设置所有任务统一的字数和段落模板。必要限制需要保留，但应与本次结论直接相关。

#### 验收重点

用户无需从大量背景中寻找答案，也不会因额外扩写得到无依据的信息。

### 12. 分离执行进度、答案和详细证据

**优先级：中。**

#### 测试发现

“我先查询……”直接进入回答正文，还出现了过程文字后粘连 Markdown 标题的问题。

#### 调优建议

将工具查询进度作为独立状态展示；最终回答保留结果与解释，表名、查询条件、记录编号等放到可查看的证据位置。

这样既让用户了解执行进度，又保留核验依据，避免内部过程占据手机首屏。

#### 验收重点

用户容易区分正在执行与已经回答；标题、表格及导出内容显示正常。

### 13. 优化多轮上下文的保留与复用

**优先级：中。**

#### 测试发现

当前多轮追问和设备切换表现较好，没有沿用历史中的999℃。后续应保留这项能力，同时减少无关历史。

#### 调优建议

重点保留当前任务目标、所选设备、数据来源、已确认定义和待解决问题。过去的读数携带采集时间与范围，不能因为出现在对话里就被当作当前事实。

同一任务中的有效证据可复用；设备、时间范围或数据模式改变时，重新检查适用性。先使用清晰的会话状态，不需要立即引入复杂长期记忆系统。

#### 验收重点

追问能够衔接，切换来源不混淆，复用数据时能说明依据及时间。

### 14. 加强运行可观察性和异常恢复

**优先级：高。**

#### 测试发现

原服务没有暴露完整工具轨迹和用量，本轮需要独立加载钩子定位失败。只看最终答案，很难区分数据库、工具、模型与前端问题。

#### 调优建议

按任务记录必要执行信息：

- 工具名称、参数、耗时和结果规模。
- 模型轮次、输入输出用量、结束原因。
- 数据是否取得、答案是否形成。
- 失败、取消和恢复发生在哪一步。

进一步验证网络中断、数据库超时、模型中途断流、取消请求及预算耗尽。恢复策略按错误类型选择，并设置执行边界，避免重复查询形成循环。

#### 验收重点

能够解释任务失败原因，也能区分很快输出过程文字与很快给出有用答案。

### 15. 建立持续评估机制

**优先级：高。**

#### 测试发现

本轮32次有效评估包含重复执行，规模不足以证明生产可靠性。需要保留基线，持续对比改前与改后表现。

#### 调优建议

每轮调优执行原有用例及新的留出用例，持续观察：

| 维度 | 主要检查内容 |
|---|---|
| 任务完成 | 是否解决所问问题；能力不足时是否准确说明 |
| 事实可靠 | 数值、来源、时间范围、结论是否有证据 |
| 执行效率 | 无效调用、输入规模、有用答案延迟及成本 |
| 用户体验 | 是否切题、是否容易读懂、是否需要反复追问 |

统计和接口约束适合自动检查；专业判断、回答重点和建议价值需要语义审阅，并逐步引入设备专业人员校准。

#### 验收重点

改进能够在多种问法、不同设备和不同时段重复出现，避免只针对本轮测试题调整。

## 三、建议实施顺序

| 阶段 | 优先实施内容 | 主要目标 | 重点复测用例 |
|---|---|---|---|
| 第一阶段 | 完成状态、数据粒度、可执行统计、证据覆盖 | 先解决无答案、算错、结论无依据 | L03、L04、L06、D01、D02、D03 |
| 第二阶段 | 元数据复用、工具筛选、历史事件接入、模型预算 | 提高复杂任务完成率，减少无效消耗 | L04、L05、D02、D08、D11、D16 |
| 第三阶段 | 上下文复用、进度与证据展示、持续评估扩展 | 提升稳定性、专业体验及可维护性 | P01、P02、D15、M01、M02及新留出用例 |

第一轮继续使用 Flash，先完成第一阶段，再用同一批测试比较效果。当前证据首先指向工具与执行链路；完成这些改进后，更容易判断模型本身还存在哪些能力限制。

## 四、实施边界

- 本文件是方案整理，没有实施上述产品改动。
- 暂不优先增加多 Agent、复杂规划框架或大量固定回答禁令。
- 保留现有只读、参数校验、执行预算与取消能力，调优不能放松这些运行边界。
- 故障根因和现场处置建议仍需要权威资料及设备专家验证。
- 改进效果必须通过真实任务和可复核证据验证，不能只以回答变短或页面正常显示作为依据。

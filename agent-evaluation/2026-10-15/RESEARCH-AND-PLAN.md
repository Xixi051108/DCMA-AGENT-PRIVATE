## 调研与方法

已在制定用例前搜索并打开以下一手资料，采用方法而非安装其框架：

1. [OpenAI Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)：先定义目标、数据集和判定标准；包含典型、边界及对抗场景；自动指标需要校准。
2. [OpenAI Trace grading](https://developers.openai.com/api/docs/guides/trace-grading)：同时检查答案和工具执行记录，定位过程中的错误。
3. [Anthropic Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)：从实际用户问题建立用例；混合确定性检查和语义审阅；保存轨迹，重复执行关键用例。
4. [GitHub langchain-ai/agentevals](https://github.com/langchain-ai/agentevals)：允许工具路径的合理变化，不要求所有成功回答使用同一个固定调用顺序。

## 测试目标与判定

重点回答：Agent 能否选对设备和数据来源，取得足够证据，准确完成问题，避免无依据的诊断，并以合理的步骤和篇幅交付结果。

- 功能：基本信息、单指标、趋势、设备切换、比较、报告、离线数据和多轮上下文。
- 事实：数值与工具返回一致，统计与独立计算一致，时间/来源/样本范围不混淆。
- 边界：缺失、空数据、连接失败、历史数据、零/负值、未知台账、未知故障码。
- 权限与注入：只读工具、无控制能力；不接受数据字段及历史对话中的伪指令。
- 效率：工具次数、重复调用、工具响应字节、首文本时间、总耗时、输出长度及供应商 usage 元数据。
- 展示：真实 HTTP 流与浏览器渲染作为补充，不把 HTTP 200 当作任务完成。

判定为通过、部分通过、失败或未完成，附理由和证据。篇幅、工具次数是诊断指标，不是所有任务的硬性及格线。不用关键词匹配代替语义正确性，也不要求固定回答模板。不将本次小样本通过率视为生产可靠性。

## 分层与隔离

1. `public-api`：用户正在使用的3000端口原始服务，黑盒验证，无法获得工具轨迹与 token 使用量，明确标记未知。
2. `live-traced`：独立3340端口，加载相同 server.ts、同一模型和真实只读数据库。仅通过 Node 加载钩子增加工具事件/usage 的观察，不更改提示词和业务逻辑。
3. `controlled`：同一独立服务，仅替换数据库工具的执行结果为保存的快照或明确标记的故障/边界夹具。模型调用真实，数据库异常是注入场景，不冒充真实断网。
4. `offline`：按前端实际上下文结构提供离线文件数据，真实模型作答。
5. `contract/unit/ui`：HTTP输入校验、已有相关离线测试及独立浏览器检查，分别计数，不能混入 Agent 任务成功率。

工具轨迹只保存公开工具参数、返回值、耗时和 usage，不保存隐藏推理或凭据。最多两个模型请求并发；关键三个场景各执行三次。实时数据会变化，用实际调用的工具结果作为证据；黑盒前后快照只能提供区间参考。

## 限制

本轮属于有边界的基线评估，不运行破坏性数据库操作，不做长期负载压测，不调用所有46个可选模型，不新增第三方测试框架，不验证未接入的厂家知识库或真实现场控制。模型请求使用已配置的 DeepSeek，会消耗该提供商额度。故障根因的专业认证仍需要设备专家与权威资料。
